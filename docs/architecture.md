# 아키텍처

## 계층

```
┌──────────────────────────────────────────────────────────┐
│ apps/web/src/app                                          │
│   서버 컴포넌트 → server 계층 직접 호출                     │
│   클라이언트 컴포넌트 → fetch로 API 호출                    │
├──────────────────────────────────────────────────────────┤
│ apps/web/src/app/api/v1                                   │
│   입력 검증(Zod) + 권한 확인 + 멱등성. 비즈니스 로직 없음    │
├──────────────────────────────────────────────────────────┤
│ apps/web/src/server                                       │
│   서비스 계층. 트랜잭션이 사는 곳                           │
├──────────────────────────────────────────────────────────┤
│ apps/web/src/providers        packages/core               │
│   외부 연동 어댑터              순수 도메인 규칙            │
│   (Mock ↔ 실제 교체 가능)       (DB·HTTP 모름)             │
└──────────────────────────────────────────────────────────┘
```

의존 방향은 아래로만 흐릅니다. `packages/core`는 아무것도 import 하지 않습니다.

## 왜 이렇게 나눴나

**규칙과 저장을 분리하면 규칙을 빠르게 검증할 수 있습니다.**
투표 창 계산, 과반수 판정, 안전조건 필터는 DB 없이 테스트됩니다.
코어 테스트 46개가 1초 안에 끝나기 때문에, 정책을 바꿀 때 즉시 확인할 수 있습니다.

**트랜잭션은 한 계층에만 둡니다.**
라우트에서 트랜잭션을 열면 어느 요청이 무엇을 잠그는지 추적이 어려워집니다.
`server` 계층에만 `$transaction`이 있고, 라우트는 그 함수를 부르기만 합니다.

## 핵심 흐름

### 코스 생성

```
응답 마감 시각 도달
      │
크론 tick ──► closeResponsesAndQueueGeneration
      │
      ├─ 제출자 0명 ──► 방장에게 선택지 반환 (연장 / 기본 코스 / 취소)
      │
      └─ 제출자 있음
             │
             ├─ 미응답자 → NO_RESPONSE (기본 설정 자동 사용 안 함)
             ├─ 제출된 취향만 집계 (알레르기·필수조건은 합집합)
             ├─ 장소 후보 조회 → 안전조건 필터
             ├─ AI 코스 생성
             │     ├─ Zod 스키마 검증
             │     ├─ 픽스 일정 보존 검증
             │     └─ 타임라인 검증          ← 하나라도 실패하면 최대 3회 재시도
             │
             ├─ votingStartedAt = 지금
             ├─ votingEndsAt = 지금 + 60분   ← 이후 변경 없음
             ├─ eligibleParticipantCount 고정
             └─ FINALIZE_COURSE 작업을 votingEndsAt에 예약
```

### 투표와 재생성

```
사용자가 싫어요
      │
   ┌──┴─────────────── 트랜잭션 ───────────────┐
   │ 1. 버전 확인 (다르면 STALE_COURSE_ITEM)     │
   │ 2. 창 확인 (코스 60분 + 항목 재투표 10분)   │
   │ 3. 투표 upsert                            │
   │ 4. 싫어요 수 집계 → 과반수 판정             │
   │ 5. 과반수면:                               │
   │      - 항목 REGENERATION_QUEUED           │
   │      - 장소를 RejectedPlace에 추가          │
   │      - AiJob 생성 (고유 제약으로 중복 방지)  │
   └───────────────────────────────────────────┘
      │
      └─► 트랜잭션 밖에서 재생성 실행
             │
             ├─ 성공: 새 CourseItem 생성 (generationVersion +1, 투표 0부터)
             │        이전 항목 REPLACED
             │        revoteEndsAt = min(지금 + 10분, course.votingEndsAt)
             │
             └─ 실패: 이전 항목을 ACTIVE로 되돌림 (기존 장소 유지)
```

재생성이 트랜잭션 밖인 이유: AI 호출은 수 초가 걸립니다.
그동안 DB 잠금을 붙들고 있으면 다른 사람의 투표가 막힙니다.
투표는 이미 저장됐으므로, 재생성이 실패해도 표는 사라지지 않습니다.

### 자동 확정

```
크론 tick (1분마다)
      │
      └─ votingEndsAt이 지난 코스 조회
              │
              ├─ 진행 중인 재생성 없음 ──► 즉시 확정
              │
              └─ 진행 중인 재생성 있음
                     ├─ 유예시간(20초) 이내 ──► WAIT, 다음 tick에서 재시도
                     └─ 유예시간 초과 ──► 재생성 취소하고 직전 항목으로 확정
```

## 시간 처리

**서버 시간이 유일한 기준입니다.**

- 모든 마감 판정은 서버에서 합니다
- API는 카운트다운 값을 초 단위로 내려주지 않고 `endsAt` + `serverTime`을 줍니다
- 브라우저는 이 둘의 차이로 자기 시계 오차를 보정한 뒤 매초 계산합니다
- 사용자의 시계가 틀어져 있어도 표시가 어긋나지 않고,
  틀어진 시계로 마감을 우회할 수도 없습니다

구현: [`use-server-countdown.ts`](../apps/web/src/hooks/use-server-countdown.ts)

## 어댑터 레지스트리

```typescript
getAiProvider()        // OPENAI_API_KEY 있으면 실제, 없으면 Mock
getPlaceProvider()     // KAKAO_REST_API_KEY 있으면 실제, 없으면 Mock
getKakaoAuthProvider() // 키 없으면 enabled: false → 화면에서 버튼 숨김
```

애플리케이션 코드는 인터페이스만 압니다.
Mock과 실제 구현이 같은 타입을 만족하므로 교체해도 호출부가 바뀌지 않습니다.

## 화면 구조

웹사이트이므로 하단 탭바 대신 상단 GNB를 씁니다.

```
src/app/
  (app)/          로그인 후 화면. SiteHeader 공통 레이아웃
    page.tsx           홈 (비로그인 시 소개 화면)
    meetings/          목록, 생성, 상세, 인터뷰
    courses/[id]/voting/   투표 화면
    records/  notifications/  settings/
  invite/[code]/  초대장. 비로그인 열람 + OG 메타태그
  login/  signup/ 헤더 없는 단독 화면
```

투표 화면은 데스크톱에서 2단입니다.
왼쪽에 코스 항목 목록, 오른쪽에 타이머 패널이 `sticky`로 붙습니다.
모바일에서는 타이머가 위로 올라가 항상 먼저 보입니다.
